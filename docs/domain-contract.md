# Доменный контракт (SSoT для констант и бизнес-правил)

Документ описывает стандарт передачи доменных констант, справочников и бизнес-правил с бэкенда (Django) на фронтенд (Alpine.js / HTMX) в модулях Midgard Nexus.

## Цели и принципы

1. **Единственный первоисточник в Python.** Все enum-значения, локализованные подписи, границы значений, допустимые переходы и декларативные правила валидации определяются исключительно на бэкенде (`constants.py`, `registry.py`, `forms.py`).
2. **Никакого хардкода на фронтенде.** JS-модули не содержат дублирующих словарей, списков enum-ключей и захардкоженных условий валидации.
3. **Fail-Fast.** Отсутствие или повреждение доменного контракта в DOM должно приводить к явной ошибке при инициализации, а не маскироваться молчаливыми fallback-значениями.
4. **Разделение статики и динамики.**
    - **Статический контракт домена** (не зависит от БД и текущего запроса) собирается один раз, кэшируется в памяти (`@lru_cache`) и инжектируется в базовый шаблон модуля через template tag.
    - **Динамические данные запроса и каталоги из БД** (списки тегов, авторов, URL-ы конкретного объекта, текущие значения полей) передаются точечно в локальный контекст конкретной страницы или оверлея (`page_opts`, `add_opts`, `overlay_opts`).
5. **Бэкенд как финальный арбитр побочных эффектов.** Оптимистичный UI допускается только для мгновенного отклика самого нажатого контрола (например, смена текста кнопки статуса или подсветка звёзд). Пересчёт связанных полей и побочных эффектов выполняется на бэкенде и применяется в UI из ответа сервера.

## Структура модуля (эталон: `vor_archives`)

```text
src/apps/<module>/
├── constants.py              # TextChoices, StrEnum, словари подписей и областей действия (scopes)
├── registry.py               # Метаданные сущностей модуля (иконки, единицы измерения, модели)
├── domain.py                 # Сборщик статического контракта get_domain_config() с @lru_cache
├── templatetags/
│   └── <module>_extras.py    # Template tag {% <module>_domain_config %} -> json_script
├── templates/<module>/
│   └── base_<module>.html    # Вызов {% <module>_domain_config %}
├── static/<module>/js/
│   └── shared/
│       └── domain.js         # Строгий ридер getDomainConfig() + resetDomainConfigCache()
└── tests/
    ├── test_domain.py        # Контрактные тесты Python (проверка полноты и рендера тега)
    └── frontend/shared/
        └── domain.test.js    # Юнит-тесты ридера JS
```

## Пошаговый чеклист для новых модулей (`fafnir_cave`, `kvasir_records`)

1. **Определить константы и правила на бэкенде:**
    - Вынести перечисления в `constants.py` (`models.TextChoices` для полей БД, `enum.StrEnum` для чисто доменных правил).
    - Описать декларативные правила форм (`requiredByType`, `conditionalRequired`) на классах форм в `forms.py`.
2. **Создать `domain.py`:**
    - Реализовать `get_domain_config() -> dict[str, Any]`, декорированную `@lru_cache(maxsize=1)`.
    - Включить только статические метаданные домена (без запросов к БД).
3. **Подключить доставку в шаблон:**
    - Добавить `@register.simple_tag` в `templatetags/<module>_extras.py`, возвращающий `json_script(get_domain_config(), "<module>-domain-config")`.
    - Вызвать тег в базовом шаблоне модуля `base_<module>.html`.
4. **Реализовать фронтенд-ридер:**
    - Создать `static/<module>/js/shared/domain.js` с кэшированием распарсенного JSON и явным выбросом `Error` при отсутствии элемента `#<module>-domain-config`.
    - Зарегистрировать алиас `@<prefix>/shared/domain` в `<module>/importmap.py`.
5. **Покрыть тестами:**
    - **Pytest (`test_domain.py`):** проверить соответствие ключей контракта первоисточникам (`constants.py`, `registry.py`, `forms.py`) и валидность вывода template tag.
    - **Vitest (`pure/*.test.js`):** тестировать чистые функции-интерпретаторы правил на **синтетических тестовых данных** (`type_a`, `type_b`, `st_a`), не дублируя реальные доменные словари бэкенда в JS-тестах.
